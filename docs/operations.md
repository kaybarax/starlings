# Operations

Detailed semantics for the `starlings` commands. The [README](../README.md) carries the quick start and command reference; this page is the full behavioural reference. `--json` works on every command; state-taking commands require `--state-dir` (or `STARLINGS_STATE_DIR`) — `init`, `examples` and `demo` need no state; project commands accept `--directory` (default: current directory; `demo` requires it and creates the directory). Commands that take leases — `lane assemble`/`resolve`/`freeze`, `stage`, `policy trust`, `revoke`, `promote`, `recover` — additionally accept `--owner` and `--lease-seconds` (default 600). The authority must be an absolute path to an existing local bare repository; remote authorities are unsupported. All Git work runs as argv subprocesses (never a shell) with hooks disabled (`core.hooksPath=/dev/null`), `GIT_TERMINAL_PROMPT=0` and only the `file` protocol allowed — except that writes to a hook-protected authority's staging and release refs run with hooks enabled so the installed `reference-transaction`/`update` hook can verify the journaled intent (see [Authority enforcement](#authority-enforcement)). Git 2.38 or newer is required for `merge-tree --write-tree`; older versions are diagnosed.

The state directory is created with mode 0700 if absent and validated with the rules in [policy.md](policy.md). It holds `starlings.db` (SQLite, WAL, foreign keys, schema-version table, short `BEGIN IMMEDIATE` transactions), `mirrors/<sha256 of authority path>.git` (a bare coordinator mirror used for all object work) and `worktrees/<batch>/<task>` plus `worktrees/runs/<run>/<check>`.

## Local assembly

```sh
starlings batch prepare demo --lanes ledger,reports --authority /absolute/authority.git
starlings task assign demo totals --lane ledger --owner worker-a
starlings task assign demo summary --lane reports --owner worker-b --after totals
starlings task handoff demo totals --head <sha> --review <review-ref>
starlings task handoff demo summary --head <sha> --review <review-ref> --prerequisite totals=<sha>
starlings lane assemble demo ledger
starlings lane resolve demo reports --task <task> --head <sha> --review <review-ref>
starlings lane freeze demo ledger
starlings stage demo --lanes ledger,reports
starlings stage demo --lanes reports --resolution <sha> --review <review-ref>
starlings status demo --json
```

- `batch prepare` reads `starlings.toml` from `--directory`, records the SHA-256 of the manifest bytes as an **untrusted** policy digest, snapshots the policy, records lane order and pins the authority staging branch as the batch base (`refs/starlings/<batch>/base` in the mirror). Identical re-runs are idempotent; different authority, lanes or manifest for the same batch is a conflict.
- `task assign` atomically claims a task (the same owner and arguments are idempotent; another claimant conflicts) and creates a worktree on `starlings/<batch>/<task>` at the base. `--after` names prerequisites that must already be assigned.
- `task handoff` requires a full commit ID present in the mirror object store and descending from the base, and retains it at `refs/starlings/<batch>/tasks/<task>`. Prerequisite SHAs must match the `--after` declarations and the prerequisites' handed-off heads; otherwise the task is parked with a reason. A parked or not-yet-included task may be handed off again.
- `lane assemble` takes the lane lease and includes handed-off tasks in assignment order (prerequisites are always assigned earlier) with `git merge-tree --write-tree` and `commit-tree`, advancing `refs/starlings/<batch>/lanes/<lane>` by compare-and-swap. A task parks if a same-lane prerequisite is not included, a cross-lane prerequisite is not yet staged, its diff from the base touches an `[assembly] excluded` glob, its head contains the handed-off head of another task in the batch that is not a declared prerequisite (directly or through the declared prerequisites' own `--after` chains), or it conflicts with the lane tip (conflicting paths are reported). Undeclared content parks with kind `dependency` and names the undeclared tasks; declared prerequisites need not be ancestors. Parked tasks other than handoff parks are retried on the next run.
- `lane resolve` accepts a resolution commit for a conflict-parked task only with `--review` and only if it contains the current lane tip and the task head; without `--review` the task stays parked. A resolution that adds an excluded path or another task's undeclared head (one not already in the lane tip) is refused and the task stays conflict-parked, so a corrected resolution can follow. The resolution is retained at `refs/starlings/<batch>/resolutions/<lane>/<task>` and becomes the lane tip.
- `lane freeze` records the tip at `refs/starlings/<batch>/frozen/<lane>`; further assembly or resolution on that lane is refused. The result lists `left_out` tasks (assigned, handed-off or parked, with state and reason) that the frozen tip does not contain; `status` shows the same per frozen lane.
- `stage` requires frozen lanes and an expiring target lease on the authority staging branch. Mode `each-lane` builds successive candidates in recorded lane order; `combined-ready` builds one candidate whose parents are the observed staging head followed by the lane tips. Each candidate is retained at `refs/starlings/<batch>/candidates/<digest>` and recorded with a `Candidate` and an `Assembly` provenance record. If `[gates.staging].scope` is not `none`, the first candidate is prepared and the command returns pending without advancing staging; it is then planned, run and landed with `promote` (below), after which the next `stage` call continues with the waiting lanes. With scope `none`, objects are fetched into the authority and the staging branch advances with `git update-ref <ref> <new> <old>`; on a protected authority the write runs through the enforcement hook, which admits it via the `prepared` candidate intent recorded before the write. If staging moved after planning, nothing is written and the result is stale. `stage` never writes the release branch. At the start of each call, `stage` reconciles journalled promotions for the staging target and refuses a target parked with `ambiguous-landing`. Whenever a round lands — here, through `promote`, or through recovery — a policy with a `[github]` table records each lane and task pull request's observed disposition through the configured adapter (`merged`, `closed-with-link` when the adapter closes an open PR with a link to the landed commit, or `closed`) into the `dispositions` table and the result entry.
- If a round conflicts with the staging head, `stage` blocks with the conflicting paths. Supply `--resolution <sha> --review <ref>` (both together; `--resolution` alone is blocked as unreviewed, `--review` alone is invalid). The option applies only to a conflicting round; in `each-lane` mode `--lanes` must name exactly one not-yet-staged lane. The resolution must be in the mirror and contain every round lane's frozen tip (otherwise invalid) and the current staging head (otherwise stale: staging moved since it was made). Paths it changes beyond the lanes' own changes that match an excluded glob, and undeclared task heads not already in staging or the lane tips, block with no write. The candidate keeps the `Candidate` shape: the resolution's tree with parents `(staging head, *lane tips)`. The resolution is retained at `refs/starlings/<batch>/resolutions/@stage/<candidate digest>` and recorded in the `Assembly` resolutions as `("@stage", "<comma-joined lanes>", head, review)`; `status` lists `stage_resolutions`.
- Lost acknowledgements: a candidate is journalled as `prepared` before the authority write. At the start of each round, if a `prepared` candidate for exactly those lanes is already contained in the staging head, `stage` reconciles it (marks the candidate, lanes and tasks staged; entry `reconciled: true`) without writing. If a round lane's frozen tip is already in the staging head with no recorded landing, `stage` refuses with status `blocked`, code `already-landed`, and writes nothing.
- `status` lists tasks (assigned, handed-off, included, parked with reason, staged), heads, reviews, lane tips, frozen state, resolutions, candidates with provenance, recorded pull-request dispositions, current authority heads and, for every handed-off task, its retained ref and whether it still matches.

Leases store absolute expiry. An expired lease can be taken over; the previous owner's later write, finalize or release is refused. Commit timestamps and identity for commits created by Starlings are fixed per batch, so rebuilding the same inputs yields the same candidate. The identity is `starlings <starlings@localhost>` unless the coordinator's environment sets `STARLINGS_COMMIT_NAME` and/or `STARLINGS_COMMIT_EMAIL`; use the same values for every command of a batch, because a different identity yields a different candidate commit.

Assembly limitations: one coordinator machine; lane-ref/journal divergence that no include intent explains is reported as stale (`lane-diverged`) rather than reconciled; ungated staging recovery covers only the lost-acknowledgement and externally-landed cases above; excluded globs use `fnmatch` semantics where `*` also matches `/`; lane resolutions are checked against them only for their diff from the lane tip; undeclared-content detection sees only handed-off heads (not unrecorded commits); task worktrees are not cleaned up; assembly leases do not supervise processes. On an authority hardened with `authority protect`, direct writes to the recorded staging and release refs are refused by the enforcement hook; anyone who can edit or disable the hook still bypasses these checks.

Initialization defaults to preview, is offline, launches no subprocesses, and only `--write` writes `starlings.toml`. It stages a complete UTF-8 file in the same directory, flushes it, then publishes by exclusive hard link. Existing files, directories and even dangling symlinks are never replaced. A crash can leave a `.starlings-*` temporary file; inspect before manual cleanup. No crash-durable directory journal is claimed. No instruction or workflow files are touched.

The generated check is a **synthetic, deliberately failing example**, not project coverage. Replace it with reviewed project commands. Presets select task, staging and release scopes; they do not claim four real check families or expected execution counts. Release-only staging may contain defects. `policy validate` validates structure, not command safety, command availability, meaningful test coverage, policy trust or successful execution. `policy show` and `policy validate` are aliases: both parse `starlings.toml` and return the same `valid`, `path`, `policy` and `warnings` result.

## Trusted policy, planning and runs

```sh
starlings policy trust --authority /absolute/authority.git --commit <sha> --review <review-ref>
starlings policy trust --authority /absolute/authority.git --commit <sha> --review <review-ref> --supersedes <current digest>
starlings signer init
starlings plan demo --gate staging [--candidate <candidate-id>]
starlings plan demo --gate release
starlings plan demo --gate task [--candidate <candidate-id>]
starlings run <plan-id> [--force-fresh] [--timeout <seconds>] [--owner <label>]
starlings cancel <run-id>
starlings check <receipt-id> [--target <branch-or-ref>]
starlings doctor --json
```

- `policy trust` reads `starlings.toml` from the named commit **in the authority** (never the working directory), validates it, stores the exact bytes as `policy/<sha256>.toml` (0600) and records authority, digest, commit, review, previous digest and time. The first trust for an authority takes `--review` only; every later trust must name the current digest with `--supersedes` (otherwise `trust-conflict`, status conflict). Re-trusting the current digest is idempotent. `trusted_at` uses the store clock. The trust record is the operator's statement that the policy was reviewed; Starlings does not inspect the review. `policy trust` takes the target leases of every target of that authority (staging and release of the new policy, the current trusted policy and every batch on the authority, plus the lane leases of task-gated batches) before recording, and is blocked with `lease-held` while any is held.
- `signer init` runs the system `ssh-keygen -t ed25519 -N "" -C starlings-verifier` to create `signer-references/verifier` (0600) and `verifier.pub`, and writes `signer-references/allowed_signers` with the principal `starlings-verifier` restricted to namespace `starlings-receipt`. It is idempotent and never overwrites an existing or inconsistent key or allowed_signers file. **The private key is unencrypted at rest**; its only protection is the operator-owned 0700 state directory. A missing `ssh-keygen` is diagnosed. Receipts are signed and verified with `ssh-keygen -Y sign/verify -n starlings-receipt`.
- `plan` uses only the current trusted policy for the batch's authority. If no policy is trusted, or the batch's recorded manifest digest differs from it, planning is blocked with `untrusted-policy`. `--gate staging` plans a `pending` staging candidate (the latest one by default). `--gate release` fetches the current authority staging and release heads, builds the release candidate with `git merge-tree` as a commit with parents `(release head, staging head)`, and retains it only at `refs/starlings/<batch>/candidates/<digest>` in the coordinator mirror; the authority's release branch is never written. A release conflict blocks with `release-conflict` and the paths (resolve on staging, review, freeze again); a release head that already contains staging blocks with `nothing-to-release`. `--gate task` plans a `pending` task candidate (the latest one by default, or `--candidate`); its target is the lane ref and its changed paths run from the lane tip to the include commit. Executor `github` is accepted on staging and release gates when the trusted policy carries a complete `[github]` table (see [Hosted execution](#hosted-execution)); the task gate and any other executor name are blocked `unsupported`. Disabled gates are `gate-disabled`.
- Selection: scope `full` selects every gate check (`selection: full`). Scope `affected` maps the candidate's changed paths (base to commit) through `[selection]` globs and selects the gate checks whose globs match (`affected`). If any changed path matches no glob of the gate's checks, any gate check has no `[selection]` entry, or nothing is selected, the plan expands to the gate's full check list (`expanded`) and lists `unmapped_paths` and `unmapped_checks`. Globs use `fnmatch` semantics (`*` also matches `/`). The plan ID is deterministic: identical inputs (candidate, trusted policy digest, gate, changed paths, selected argv, globs, artifacts, exclusives, limits, guest image) return the same plan with `repeated: true`.
- `run` refuses a plan whose policy is no longer trusted (`stale-plan`) and requires a signer (`no-signer`). It takes a per-plan run lease, so a concurrent run of the same plan is blocked (`lease-held`). Unless `--force-fresh` is given, a stored passed receipt for the same plan that passes a full `check` is reused (`reused: true`). Checks run sequentially in plan order. Before each check, admission atomically acquires, in one SQLite transaction, one of `limits.cpu_slots` CPU slot leases, one of `limits.max_guests` guest slot leases for guest checks, and every `[exclusive]` resource of the check; if any is unavailable the run **waits** (polling, still cancellable) rather than failing. The budget is host-wide for the state directory, sized by the plan's trusted limits. Leases are released only after the check's process group is confirmed empty.
- Each check gets a fresh detached worktree of the candidate commit under `worktrees/runs/<run>/<check>` (removed afterwards), a private job directory from the system temporary directory used as `HOME` and `TMPDIR` (removed afterwards), and an environment reduced to `PATH`, `LANG`, `LC_ALL`, `HOME` and `TMPDIR` (no `GIT_*`, no state or signer paths). It starts in a new session with stdin closed and stdout/stderr streamed to `logs/<run>/<check>.out` and `.err` (0600). The timeout is `limits.timeout_seconds`; `--timeout` may only lower it. On timeout, `cancel`, or SIGINT/SIGTERM to the runner, the process group gets SIGTERM, a grace period (2 s), SIGKILL, then the leader is reaped and `os.killpg(pgid, 0)` is polled until the group is gone. Stray group members left after a normal exit are reaped the same way. A group that cannot be confirmed empty leaves its slot leases to expire and the run fails `unreaped` without a receipt. For an executor-`github` plan the run submits each check to the configured host adapter instead of starting a local process; see [Hosted execution](#hosted-execution).
- Required `[artifacts]` files (regular files, no symlinked path components) are copied to `artifacts/<run>/<check>/<path>`; a missing one fails that check (`missing-artifact`). Logs and artifacts are hashed with SHA-256. Each check stores an `Evidence` record whose artifact digest covers its file manifest. When every planned check completed (passed, failed, timed out or missing an artifact), a `Receipt` is signed, stored in the database and written to `evidence/<run>/receipt.json` with `receipt.json.sig`; the outcome is `passed` only if every check exited 0 with all artifacts present. **A timeout counts as a completed failure and yields a signed failed receipt.** Cancelled or interrupted runs (and guest-unavailable runs) never sign; their evidence is retained. Failed evidence is never deleted. Run exit status: 0 passed (or reused), 7 failed outcome, cancelled, interrupted, unreaped or guest-unavailable.
- Resources: `memory_mib` and `disk_mib` are recorded per check, not enforced for native checks. Each evidence row reports the process-wide `ru_maxrss` high-water mark of reaped children (bytes; it covers all children the runner has waited for, not just this check, and misses grandchildren not waited for by their parent) and the checkout's on-disk size after the check. Guest checks get `--memory` of `memory_mib / max_guests` and `--cpus 1`.
- Guest environment: `docker run --rm --pull never --network none --cpus 1 --memory <m>m --mount type=bind,source=<checkout>,target=/work -w /work --name starlings-<run>-<check> <image> <argv>`. The docker CLI receives the operator environment minus `GIT_*` and `STARLINGS_*`; the container receives none of it. Before a guest run, `docker info` must succeed and the pinned `[guest] image` must be present locally; otherwise the run fails `guest-unavailable` with no fallback to native. The checkout must be on a path shared with the docker VM (for Colima, the home directory by default); a bind source the daemon cannot see fails the check with `guest-unavailable` instead of mounting an empty directory. Timeout or cancellation runs `docker kill` and polls `docker ps -a` until the container is gone, then reaps the client's process group.
- `check` returns `valid` (exit 0), `invalid` (exit 2), `stale` (exit 6) or `failed` (exit 7, a correctly signed receipt that records a failed outcome), with reasons and `authorizes: true` only when valid. Invalid: the record does not match its ID, plan or candidate; the signature does not verify against `allowed_signers`; any retained log or artifact is missing or its SHA-256 differs; evidence IDs do not match the retained evidence for every planned check; or the receipt target differs from `--target` (default: the plan's target). Stale: the policy digest is no longer the authority's trusted policy, the verifier fingerprint is not the current signer, or the target no longer equals the candidate base (staging moved for a staging receipt; release moved for a release receipt; the mirror lane ref moved for a task receipt). Invalid takes precedence over failed, and failed over stale: a failed receipt keeps reporting `failed` after its target moves, with the stale reasons listed.
- `cancel` sets a flag that the runner polls between and during checks; it reports the run's state if it is not running.
- `doctor` additionally reports the Git version check, `ssh-keygen` location, whether a signer exists in the state directory, docker daemon reachability and Colima status. Given `--authority`, its `enforcement` section probes the authority: whether a protection record exists, which refs it covers, and whether both hook files are installed and byte-identical to the recorded digest; `enforcement_implemented` is `true` only when the record exists and both files match it, and `mode` honestly reports `coordinator-enforced` when the hook is absent. Its `adapters` section reports the configured `[github]` adapter, its gated gates, and for `fake` the event-store path and recorded run/PR/event counts (for `github`, whether the `gh` CLI is on `PATH`; the adapter is live but unqualified). It runs only read-only probes (`git --version`, `docker info`, `colima status`) and never starts anything.

Same-login trust: native checks run as the operator's user. They cannot see the signer path or state directory in their environment, but their working directory is inside the state directory, a worktree's `.git` file points into the coordinator mirror, and nothing prevents a hostile check from reading the unencrypted key or altering state. A descendant that calls `setsid` (or `setpgid`) leaves the process group and escapes tracking on macOS. Use native execution only for trusted contributors. The docker guest isolates the network and filesystem view but is not certified as a security boundary.

Run limitations: checks within a run execute sequentially (admission bounds concurrency across runs); memory and disk are measured, not enforced, for native checks; a descendant that escapes its process group is not tracked; the signer key is unencrypted.

## Approvals, promotion and recovery

```sh
starlings approve <plan-id> --by <identity> --expires-in <seconds> [--review <review-ref>]
starlings revoke <approval-id>
starlings promote <plan-id> --receipt <receipt-id>
starlings recover <batch>
starlings recover <batch> --resolve <promotion-id> --as landed|not-applied
```

- Approvals: each `[gates.*]` table accepts an optional integer `approvals` (0–16, default 0; booleans rejected); presets do not set it. `approve` records an `Approval` for a plan with an expiry of 60 to 2592000 seconds from the store clock. An identity holds at most one live approval per plan: repeating it with the same review returns the existing record (`repeated: true`), a different review conflicts (`approval-exists`); after expiry or revocation a new one may be granted. `revoke` takes the plan's target lease, so it serializes with promotion; if a promotion holds the lease it is blocked (`lease-held`) and the caller retries.
- `promote` takes the target lease (the same `target:<authority>:<ref>` resource as `stage`; the lane lease `lane:<batch>/<lane>` for the task gate), reconciles that target's journal (below) and refuses a parked target (`ambiguous-landing`). It then rechecks everything under the lease: the receipt must belong to the plan and `check` as valid (signature, retained files, trusted policy digest, signer, target, base equal to the current target head); a failed receipt is refused with `receipt-failed` (exit 7), an invalid one with `invalid-receipt`, a stale one with `stale-receipt`. The plan's gate must have its required number of live (unexpired by the store clock, unrevoked) approvals (`approval-required`). Sources must be unchanged (`stale-source`): staging — every candidate lane still has the same frozen tip and is not yet staged, and the candidate is still pending; release — the authority staging head still equals the candidate's staging parent; task — the mirror lane ref and journal tip equal the candidate base, the task is pending with the same reviewed head and its retained task ref is unchanged.
- The promotion is journalled first: one transaction re-checks the lease, live approvals and trusted digest and inserts a `promotions` row in state `intent` with the receipt, approval IDs, authority, repository, target, old and new commit, tree, parents and sources. Hook `before-write` follows; candidate objects are fetched into the authority without creating refs (not needed for task targets, which live in the mirror); then one `git update-ref --stdin` transaction runs `start`, a `verify` for each source ref in the same repository (release: `refs/heads/<staging>` at the staging parent; task: the retained task ref at the reviewed head), `update <target> <new> <old>`, `prepare` and `commit`. On a hook-protected authority this transaction runs with hooks enabled, so the installed `reference-transaction` hook calls `authority check-intent` and confirms the `intent` row before the update commits; if the recorded hook is missing or modified, `promote` and `stage` refuse with `unprotected-authority` unless `--allow-unprotected` is given, which proceeds with hooks disabled. A refused transaction marks the promotion `not-applied` (a staging candidate becomes `stale`) and returns stale with nothing written. After hook `after-write`, the landed ref, tree and parents are verified against the candidate; the promotion becomes `landed` with a `Promotion` record, and the state is finalized: staging marks the candidate, lanes and tasks staged; release records the landing in the promotion; task includes the task (state `included`, lane tip advanced, resolution recorded if any). A promote of a (plan, receipt) that already landed returns `repeated: true` without a lease. Concurrent promotes serialize on the lease: one lands, the other is blocked and later repeated; a different candidate for the same target after a landing is stale.
- `refs/heads/<release>` in the authority is written only by `promote` with a release receipt. **Deployment is out of scope**: a release landing records an exact commit and authorizes nothing else.
- Task gate (`[gates.task].scope` not `none`, as in `every-task-lane-release`): `lane assemble` builds the include commit for the next eligible task, retains it as a task candidate (`Candidate` targeting the lane ref, `Assembly` with that one task) in `task_candidates`, sets the task to `pending`, stops assembling the lane and returns pending (exit 4). Repeating `assemble` while the candidate's base is still the lane tip returns the same candidate (`repeated: true`); if the tip moved the candidate becomes `stale` and the task is re-evaluated. `lane resolve` under the task gate likewise records the reviewed resolution as a pending task candidate instead of including it. After `plan --gate task`, `run` and `promote`, the lane ref advances and the next `assemble` continues. A pending task's handoff cannot change.
- Recovery: `recover <batch>` takes each relevant lease in turn (staging and release targets, every lane, and the run lease of every `running` run) and reports every action. The same target reconciliation runs automatically at the start of `promote` and `stage` for that target, and lane reconciliation at the start of `lane assemble`, `lane resolve` and `lane freeze`. A promotion in `intent` is resolved from the actual target ref: equal to `new` — finished as landed (`recovered: true`); equal to `old` — `not-applied` (retry allowed); anything else — `ambiguous`, which parks the target: `promote` and `stage` on it refuse with `ambiguous-landing`, and `recover` returns blocked, until the operator runs `recover <batch> --resolve <promotion-id> --as landed|not-applied`. `landed` is accepted only if the observed ref is or contains `new` (and `new` has the candidate's tree and parents); `not-applied` only if the observed ref does not contain `new`. A finalize that finds its promotion already reconciled by another coordinator is refused (`lease-lost`) and writes nothing.
- Include intents: before advancing a lane ref, `assemble` and `resolve` journal `(lane, task, old, new)` (hooks `include-before-write`, `include-after-write`). On the next lane command the intent is finished (lane ref equals `new`), dropped (equals `old`) or left in place with the lane stale `lane-diverged`, whose message names the intent.
- Lost runs: a `running` run whose run lease has expired (by the store clock) is marked `interrupted`; the process groups recorded at process start are killed with SIGKILL and confirmed empty, guest containers named for the run are stopped, its slot leases are released, its job directories removed and its run worktrees removed with `git worktree remove --force` and `git worktree prune`. Recovery never signs; a run whose lease is still live is skipped.
- `status` also lists task candidates, promotions (state, observed ref, operator resolution, record), approvals (with `live`) and include intents.

Promotion and recovery limitations: one coordinator machine and a local bare authority; on a protected authority the enforcement hook refuses unrecorded staging/release writes, but it is not credential separation — anyone who can edit, delete or bypass the hook still bypasses every check; staging promotions verify lane sources from the journal and the mirror, since frozen refs are not in the authority; recovery kills recorded process groups by ID and cannot prove the group was not reused after a very long outage, and a crash between process start and recording leaves that group untracked; a stalled old coordinator whose lease expired can still race one ref write, which the compare-and-swap old value bounds but whose journal row may then read `not-applied` while another row records the single landing; trust leases do not cover task-gated lanes of batches created later; `landed_at` is the store-clock time of finalization, which for a recovered landing is the time of recovery.

## Diagnosing a failed release gate

```sh
starlings diagnose <batch> --gate release --receipt <receipt-id>
starlings diagnose <batch> --gate release --receipt <receipt-id> --plan <plan-id> --checks journeys,ledger
```

- `diagnose` attributes a failed release gate to a task, a lane or a lane pair. Preconditions: the batch exists and `--receipt` is a recorded **failed** receipt for a release plan of that batch (`--plan` optionally pins the plan). A passed receipt is refused (`nothing-to-diagnose`); a receipt from another batch or gate is invalid. Without `--checks`, the checks re-run are exactly the checks that failed in the receipt's run (in plan order); `--checks` narrows that to named plan checks.
- **Basis.** Diagnosis never consults the landed staging or release state. The sources are the batch's lanes whose recorded frozen tips are still the values of `refs/starlings/<batch>/frozen/<lane>` in the coordinator mirror and are contained in the release candidate's staging parent; lanes not contained are listed as skipped. Each subset candidate is built like `stage`: `git merge-tree --write-tree` merges the tips onto the release head (the candidate's release parent) and `commit-tree` records parents `(release head, *tips)`. Every candidate commit is retained only in the mirror at `refs/starlings/<batch>/diagnostics/<commit>` and every probe — basis (lane, lane pair, task prefix or single task), commit, ref, conflict and per-check outcome — is recorded in the `diagnostic_runs` table (schema 4) in order.
- **Probe order.** First the release head alone: if it fails, the batch is not required for the failure and subset probing stops. Then one candidate per source lane, in lane order. A lane that fails alone is bisected within its ordered included tasks — prefix candidates use the retained lane include commits, so lane history including reviewed resolutions is replayed exactly — and the boundary task of the smallest failing prefix is probed once alone from its reviewed head. The prefix probes plus the boundary probe share a cap of `ceil(log2(n)) + 2` candidate runs per lane; hitting the cap reports the best known bound (`capped: true`). If no single lane fails, every unordered lane pair is probed (quadratic in the lane count) for the interaction case.
- **Attribution.** The result lists the ordered candidates with per-check pass/fail, each bisection (probes, smallest failing prefix, boundary task with retained ref and head, whether the boundary alone fails) and a final `attribution`: `task` (single responsible task), `lane-interaction` (the failure first appears at a task that passes alone), `lane` (single failing lane, bisection capped), `multiple-lanes` (several lanes fail independently, each bisected), `lane-pair` (interaction defect), `baseline` (the release head already fails) or `inconclusive` with reasons.
- **Diagnostics never authorize.** Diagnostic runs reuse the runner's admission slots, worktrees, environment scrubbing, timeouts and process-group reaping, but write only to `diagnostic_runs`: no `runs` or `evidence` rows, no receipt is signed, and nothing is written to the receipts or promotions tables. No diagnostic ID is a receipt ID, so `promote` refuses every one of them (`unknown receipt`), and a failed release receipt stays `receipt-failed`. Diagnosis takes a `diagnose:<batch>` lease to serialize concurrent diagnostics and the same per-check slot leases as `run`.
- Limitations: a killed diagnose is not recovered — its subset worktrees and any recorded process groups are left until their slot leases expire (the `processes` column keeps the last known groups); bisection assumes failure appears monotonically by prefix and treats a merge-conflicting subset as not-failing; a boundary task included through a conflict resolution is probed from its reviewed head, not the resolution; guest checks reuse the same guest path but are unqualified for diagnostics; triads and larger interactions report `inconclusive`.

## Authority enforcement

```sh
starlings authority protect --authority /absolute/authority.git
starlings doctor --authority /absolute/authority.git --json
```

- `authority protect` hardens a local bare authority against unrecorded writes to its staging and release refs. The protected ref set is fixed at protect time from the current trusted policy's `staging` and `release` branches (falling back to every batch recorded for that authority); it is not re-derived later, so re-protecting after a trusted policy that renamed branches reports a conflict rather than silently changing the set. It generates one deterministic shell script — the interpreter, the starlings package location, the absolute state directory and the absolute authority path are baked in — installs it mode 0755 as both `hooks/update` (which fires on `git push`) and `hooks/reference-transaction` (which fires on `git update-ref`, including `--stdin` transactions, and on push), and records the script's sha256 and the protected refs in an `authorities` table row (schema version 4). It takes the target leases of every protected ref, so it serializes with `stage` and `promote`. Repeating with identical inputs is idempotent; a hooks file that exists with different content or a protection record with different inputs is a conflict and nothing is overwritten.
- The hook calls `starlings authority check-intent --state-dir <state> --authority <authority> <refname> <old> <new>` for every ref update (per line of the reference-transaction input). `check-intent` opens the state database read-only and exits 0 for a non-protected ref, or for a protected ref only when the journal holds a matching intent: a `promotions` row for that repository and target with the same old and new values in state `intent` (the CLI wrote it before the ref write) or `landed` (an exact replay), or — for ungated staging — a `candidates` row in state `prepared`/`staged` whose record names that authority, target, base and commit. A `verify` line inside an `update-ref --stdin` transaction is reported to the hook as `<old> <zeros> <ref>`, indistinguishable from a deletion at that layer; it is admitted only when a journaled intent names the ref and old value among its recorded `sources` — a real deletion or rewrite outside a journaled promotion is refused, as is a push to a protected branch.
- `stage` and `promote` detect a recorded, unmodified hook and run their authority ref writes with hooks enabled, so the hook observes the intent at write time. If a protected authority's hook files are missing or differ from the recorded digest, both commands refuse with `unprotected-authority` (status blocked) unless `--allow-unprotected` is passed, which writes with hooks disabled. `doctor --authority` reports `recorded`, `installed`, `unmodified` and per-hook-file state; `lane resolve` and task-gate writes go to the coordinator mirror and are unaffected.
- Enforcement guards against drift and accidents, not credential separation: the hook only consults the recorded intent, an `intent` row is visible to it the moment `promote`/`stage` journals it, and a same-login writer who edits or deletes the hook files or passes `core.hooksPath=/dev/null` to git bypasses it entirely.

## Hosted execution

```sh
starlings templates github --directory <project>            # preview (default)
starlings templates github --directory <project> --write    # exclusive write into .github/workflows
```

A staging or release gate may name `executor = "github"` when the trusted policy carries a `[github]` table (`docs/policy.md` has the schema). The task gate stays local-only; hosted gates require environment `native`; a local-executor profile submits zero adapter jobs and never touches the adapter store.

For each planned check, `run` submits one job to the configured adapter with the repository, the pinned `workflow` caller and `reusable_workflow` (`path@<40 hex>`) revision, the exact candidate head SHA and the submission event (a `pull_request`-style base-and-source routing record). The fake adapter validates that event against the routing registered for the caller workflow — the github-gated target branches and their allowed source refs — so a push to an unlisted ref or a PR from an unlisted source triggers nothing. The run polls `completion` for up to the per-check timeout. Evidence and receipts keep the existing mechanism: the receipt signs the same candidate, plan, outcome, evidence IDs and retained files, and each check's evidence metrics record the host binding (`adapter`, `host`, `repo`, `event`, `run_id`, `attempt`, `workflow`, `revision`, `head_sha`). Only `completed` with conclusion `success` and all required artifacts passes a check; `skipped`, `cancelled`, `timed_out` or `failure` conclusions, or a declared missing artifact, fail it. A completion event whose head SHA differs from the submitted candidate is rejected as `stale`.

`check` additionally verifies every host-binding field against the plan's policy and candidate, and every recorded run/attempt against the configured adapter's event log — a wrong attempt, workflow revision, head SHA or absent event is `invalid`. `promote` uses a valid hosted receipt exactly like a local one.

A run whose submission is accepted but whose completion never arrives returns `pending` (exit 4) with the run left in state `running` and no receipt; `recover` marks it `interrupted`, and a later `run` resubmits the job (the fake increments the attempt on the same run ID). The all-local profile never creates `adapters/fake.json`.

`templates github` renders the two packaged workflows for a `[github]` policy: the project-owned caller (triggers restricted to the configured target branches under `pull_request`, `merge_group` and `workflow_dispatch`, `permissions: contents: read`, and the reusable reference pinned exactly as `github.reusable_workflow`) and the parameterized reusable check job (`workflow_call` inputs, `actions/checkout` pinned by full commit ID). It previews by default, refuses to replace existing files like `init`, and nothing writes `.github` without it.

`adapter = "github"` selects the live adapter (`adapters/github.py`), which runs every host interaction through the `gh` CLI (`gh api` for the REST API, `gh run` for artifacts and `gh pr` for pull requests) under the operator's own `gh` authentication — starlings never reads, prints or stores credentials and never opens a socket itself; every `gh` call has a timeout and API failures surface as adapter errors. For each check it uploads the candidate's objects through the Git data API — blobs, then trees, then commits in parent-first order, each verified byte-identical by SHA — and retains the commit at `refs/starlings/candidates/<sha>` so the workflow can check it out. GitHub's dispatch endpoint accepts only a branch or tag name for `ref`, never a commit SHA, so a SHA-pinned `reusable_workflow` revision is first held under the deterministic branch `starlings/workflow-pin/<sha>`; the workflow file that runs is still exactly the pinned revision. The created Actions run is matched by a `starlings/<run-id>/<check-id>` token in its `run-name` (the dispatch endpoint returns no correlation ID), and on completion the `starlings-<run-id>-<check-id>` artifact — `result.json`, `stdout.txt`, `stderr.txt` and a `staged/` tree of the declared artifacts — is downloaded into the same result shape the fake produces, so evidence, binding fields and `check` verification are unchanged. A JSON journal at `adapters/github.json` under the state directory records registered workflows, submissions, observed completions and PR close links; `event_log` replays those events and refreshes unfinished submissions from the live API. Routing is still enforced locally at submission time exactly as with the fake — GitHub `pull_request` triggers cannot filter head branches.

The live adapter is implemented but **unqualified**: a rehearsal against a private repository proved dispatch, routing, result-artifact binding and pull-request dispositions end to end, but a passing hosted gate could not be exercised during rehearsal, so none has been recorded. Real event delivery guarantees (webhook ordering, retries, merge-queue semantics), branch protections and required checks, hosted usage limits, runner parity between the reusable workflow and local/guest checks, and credentials and permissions all remain unproven until a green hosted run is recorded on a working hosted environment. Honest limits: object upload is one API call per blob, tree and commit, and each SHA-pinned workflow revision leaves a `starlings/workflow-pin/<sha>` branch in the repository — the only dispatchable form GitHub accepts for a pinned commit.
