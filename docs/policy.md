# Policy schema 1 and contracts

`starlings.toml` is a TOML manifest validated as schema 1. `starlings init --preview` prints the complete rendered example. All fields in that output are required except disabled gates may omit `executor`, `environment` and `checks`. Unknown fields are errors at every table. The optional `[assembly]` table accepts `excluded`, a duplicate-free array of relative path globs; tasks whose changes touch a matching path park during assembly. Optional tables keyed by existing check IDs (unknown IDs are errors), each value a nonempty duplicate-free array: `[selection]` relative path globs whose changes select the check under scope `affected`; `[artifacts]` normalized relative file paths (no `.`/`..`, no glob characters) the check must produce; `[exclusive]` resource names (`[a-z0-9][a-z0-9._-]*`, for example `port-5432`) the check holds exclusively. `[guest]` has exactly `image`, pinned as `name@sha256:<64 lowercase hex>`, and is required when any enabled gate uses environment `guest`. `[github]` accepts optional `adapter` (`fake` — the default when omitted — or `github`), `host` (a nonempty label recorded in receipt bindings), `reusable_workflow` (pinned as `path@<40 lowercase hex>`) and `workflow` (a project caller path `.github/workflows/<name>.yml|yaml`); `reusable_workflow` and `workflow` are required when any enabled gate uses executor `github`, and hosted gates require environment `native`. The optional `[identity]` table has exactly `name` and `email` (no angle brackets): the author and committer of every commit Starlings creates, instead of the default `starlings <starlings@localhost>`. The optional `[environment]` table sets what native checks inherit from the operator: `home` is `isolated` (the default: a private job directory is `HOME`) or `operator` (the operator's own `HOME`), and `pass` is a duplicate-free array of environment variable names whose operator values are handed to every native check; `GIT_*`, `STARLINGS_*`, `HOME`, `TMPDIR`, `PATH`, `LANG` and `LC_ALL` cannot be named. Both widen what a check can reach and are part of the reviewed policy (see [operations.md](operations.md#trusted-policy-planning-and-runs)). Presets omit these tables. `project` is a nonempty name; `staging` and `release` are distinct Git branch names. `fully_verified_release = true` requires release scope `full`.

The gates are `task`, `staging`, `release`. Scopes: `none`, `affected`, `full`. Staging mode: `each-lane` or `combined-ready`. Enabled gates require a nonempty, duplicate-free list of existing check IDs plus executor (`local`, `github`) and environment (`native`, `guest`). Disabled gates remain fully structurally validated. Checks are nonempty argv arrays, never shell strings; empty non-executable arguments are allowed. Check IDs use lowercase letters, digits, hyphens and underscores, starting with a letter. Each gate also accepts an optional integer `approvals` (0–16, default 0; booleans rejected). The validator never evaluates commands. There is no check-dependency graph in schema 1; gate-to-check references are the only execution dependencies.

Positive integer limits: `cpu_slots` (up to 1024), `memory_mib` (up to 2^30), `disk_mib` (up to 2^40), `timeout_seconds` (up to 604800). `max_guests` is an integer 0–1024; enabled guest gates require at least 1. Booleans are not integers. `cpu_slots`, `max_guests` and `timeout_seconds` are enforced by the runner; `memory_mib` and `disk_mib` are recorded (and bound guest memory) but not enforced for native checks. Executor `github` is usable on staging and release gates through the configured `[github]` adapter; the task gate remains local-only in v1 (`plan` blocks it `unsupported`), as does any other executor name. With `adapter = "fake"` (the default) hosted checks run against a deterministic local simulation stored at `adapters/fake.json` under the state directory — offline-qualified for routing, binding, dispositions and recovery only. With `adapter = "github"` each check is submitted to the real repository as a `workflow_dispatch` through the `gh` CLI — the candidate's objects are uploaded over the Git data API and a SHA-pinned reusable workflow revision is dispatched via a deterministic `starlings/workflow-pin/<sha>` branch; the adapter is implemented but unqualified (no passing hosted gate has been recorded; see the hosted-execution section of [operations.md](operations.md)). Every check's evidence binds `adapter`, `host`, `repo`, submission `event`, `run_id`, `attempt`, `workflow`, `revision` and `head_sha`, and `check` verifies them against the plan, the candidate and the adapter's event log — a wrong attempt, workflow revision or head SHA is `invalid`.

`authority.mode` is `local-bare` or `mirror`. In both, local bare refs are the authority. `mirror` adds a required `upstream` (an absolute path, a `file:///`, `https://` or `ssh://` URL, or `host:path`; no whitespace, no transport helpers, no embedded credentials) and an optional boolean `publish_staging` (default false): the authority follows that upstream with `authority sync` and copies a landed, verified release to it with `authority publish` (see [operations.md](operations.md#mirror-authority)). `local-bare` accepts no other key. The authority is a local bare Git repository with frozen source refs and expected-target updates in one ref transaction, under exclusive coordinator control. The authority path is supplied per batch to `batch prepare`; `doctor` does not register or inspect it. A direct Git writer can bypass a CLI; future enforcement requires actual exclusive credentials or equivalent server controls. Remote authorities and GitHub enforcement remain unsupported: a mirror's upstream is never read as an authority.

## Contracts

`starlings.contracts` supplies frozen `Candidate`, `Plan`, `Evidence`, `Receipt`, `Adapter`, `Assembly`, `Approval` and `Promotion` records. Schema is integer 1, except `Plan`, which is schema 2. IDs are `<kind>:<sha256>` over ASCII canonical JSON (sorted keys, compact separators, escaped Unicode) containing schema, kind and all typed fields, excluding ID. Tuple order is identity-significant. IDs are content identities, **not signatures**. Candidate binds repository/authority labels, target, base, ordered parents, tree and exact commit; plan binds candidate ID, trusted policy digest, gate, selected checks, execution location, selection (`full`, `affected`, `expanded`) and an inputs digest; evidence records one check outcome and artifact digest; adapter describes name, version and capabilities; assembly binds a candidate ID to the batch, ordered lanes, ordered entries `(task, lane, head, review, ((prerequisite, head), ...))` and resolutions `(lane, task, head, review)`. Approval binds plan ID, candidate ID, `by`, review (or null), `granted_at` and `expires_at`; promotion binds plan ID, receipt ID, ordered approval IDs, target, old and new commit, tree, ordered parents and `landed_at`. Candidate and receipt targets are a fully qualified branch ref or a task-gate lane ref `refs/starlings/<batch>/lanes/<lane>` (existing IDs are unchanged). Receipt binds candidate ID, plan ID, target, base, commit, tree, policy digest, outcome (`passed`, `failed`), ordered evidence IDs, ordered `(retained path, sha256)` artifact and log digests, verifier (`version`, signer `fingerprint`), executor, environment, toolchain (`python`, `git`, `platform`, `guest_image` or null) and `issued_at`. The signed payload is the receipt's canonical JSON (including its ID); the SSH signature is stored beside it and is not part of the ID. `Receipt.from_dict` rebuilds and re-identifies a stored receipt. Approvals are separate records checked live at promotion, not part of the signed receipt. Never treat constructing a record as proof that it happened; only `check` evaluates a receipt.

## Private state

`doctor --state-dir /absolute/private/path` describes, validates and never creates state. Default: `~/.local/state/starlings`. State must be separate from the checkout (neither ancestor nor descendant), with no symlink components. An existing root and known entries must be operator-owned and inaccessible to group/other; directories need mode 0700 or stricter and files 0600 or stricter. Known children: `starlings.db` (with its `-wal` and `-shm` files), `mirrors/` and `worktrees/` (created by assembly commands), `policy/` (trusted policy blobs), `signer-references/` (signer key, public key, allowed_signers), `logs/`, `artifacts/` and `evidence/` (per-run retained files and receipts), `adapters/` (the offline fake host's JSON event store), all created on demand with mode 0700 directories and 0600 files, plus the reserved `journal.sqlite3`. These checks are not a race-proof file-opening authority or sandbox. The database schema is version 5: versions 1–4 databases are upgraded in place in one transaction by adding the verifier, promotion, diagnostic, authority and disposition tables and rebuilding `tasks` to allow state `pending` (foreign keys are checked before commit).

## Output and exit statuses

`--json` works before or after subcommands. JSON responses use `schema`, `ok`, and either `data` or `error` (`code`, `message`). Assembly commands also include `status` (`ok`, `pending`, `parked`, `blocked`, `stale`, `failed`); errors may carry `error.data`. Exit statuses: 0 ok; 2 usage, invalid input or invalid policy/state configuration (including unsupported Git); 3 filesystem/missing-file/conflict errors, including a conflicting re-prepare, a task claimed by another owner or an existing workflow template; 4 pending (staging or task candidate prepared, target not advanced; or a hosted run whose accepted job delivered no completion within the bounded poll — `recover` marks it interrupted and a rerun resubmits); 5 parked or blocked (tasks parked, lease held, lane frozen or not frozen, staging conflict, unreviewed or excluded or undeclared staging resolution, already landed, untrusted policy, release conflict, nothing to release, unsupported gate, missing signer, missing approvals, ambiguous landing, refused operator resolution, recovery that skipped a held lease or left a target parked); 6 stale (compare-and-swap or ref-transaction failure, moved target or source, lost lease, stale plan or stale receipt; nothing further written); 7 failed (Git or database failure, failed run or receipt outcome including a promotion refused for a failed receipt, cancelled, interrupted, unreaped or guest-unavailable run). `check` reports invalid receipts with exit 2 and status `invalid`. Unsupported later commands fail with status 2, never fake success. Human help/version use standard argparse formatting; `--version --json` returns the JSON envelope. `doctor` is read-only inventory, not a readiness certificate; a missing manifest is informational.
